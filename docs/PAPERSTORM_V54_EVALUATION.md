# PaperStorm v5.4：真实 RAG 与 Context Engineering 评测

## 结论先行

v5.4 的核心不是把分数写得更高，而是建立一套可审计的评测闭环：真实 Zotero PDF、按论文隔离的 dev/test、人工审核门禁、Bootstrap 置信区间、质量与延迟联合选型，以及可恢复上下文压缩的真实论文对照。

当前数据状态是 **自动候选（candidate）**，不是人工金标。115 条候选包含 55 条 dev 和 60 条冻结 test 候选；人工审核数为 0。只有至少 50 条有效 test 问题完成审核，且领域数量满足门禁后，代码才会读取冻结 test 并允许生成可发布指标。

## 数据与防泄漏协议

- 来源：40 篇本地 Zotero PDF，共 868 个 chunk；不修改原 PDF。
- 可评测论文：23 篇，形成 115 条中文跨语言检索候选。
- 划分单位：`document_id`，同一论文的所有 chunk 和问题只能进入同一个集合。
- 开发集：55 条候选，只用于比较 BM25、Dense、Hybrid 和 Rerank。
- 冻结集：60 条候选；人工门禁未通过时，评测函数不会读取其排名和标签。
- 标签治理：自动问题只能用于工程诊断；人工审核可以判无效、改写问题、修改相关论文和判断证据充分性。
- 结果治理：数据集哈希变化后旧审核失效；网页显示候选、小规模实验、可发布三档证据等级。

这套设计解决了原 v5.2 的关键缺陷：只有 46 条自动问题、test 仅 12 条，既不能达到 50 条人工门槛，也容易把一次小样本结果误写成正式 benchmark。

## 真实检索实验

### 配置

- 任务：中文问题检索对应真实论文，Top-K=5。
- Embedding：`paraphrase-multilingual-MiniLM-L12-v2`。
- Reranker：`mmarco-mMiniLMv2-L12-H384-v1`。
- 候选集：55 条 dev 自动候选；每项置信区间使用 2,000 次 bootstrap。
- 延迟预算：P95 不超过 500 ms；超过预算的配置不能成为默认部署方案。

### Dev 实测

| 方法 | Recall@5 | MRR | nDCG@5 | P95 延迟 |
| --- | ---: | ---: | ---: | ---: |
| BM25 | 0.0909 | 0.0909 | 0.0909 | 248.5 ms |
| Dense | 0.3273 | 0.2606 | 0.2773 | 234.8 ms |
| Hybrid（部署选择） | 0.3636 | 0.2530 | 0.2814 | 335.7 ms |
| Hybrid + Rerank（质量最优） | 0.4000 | 0.3485 | 0.3617 | 3252.7 ms |

Hybrid 相比 BM25 的 Recall@5 提高 0.2727，说明跨语言语义召回与词法召回互补。Rerank 继续提高了 MRR 和 nDCG@5，说明二阶段模型更擅长把相关论文排到前面；但 CPU P95 达到 3.25 秒，超过 500 ms 预算，因此系统选择 Hybrid，而不是为了更漂亮的离线分数默认开启 Rerank。

这些数值只能称为 **真实语料 dev 候选实验**。它们可以证明实现、测量方法和工程权衡，不能证明未知问题上的最终泛化质量。冻结 test 指标必须等人工审核完成后重新生成。

## 真实论文 Context 对照

20 个场景使用真实论文证据构造多轮调研上下文，对比完整历史、固定窗口和结构化压缩：

| 策略 | 平均输入 Token | 节省率 | 约束保留 | 来源保留 | 精确恢复 |
| --- | ---: | ---: | ---: | ---: | ---: |
| Full history | 1799.2 | 0% | 100% | 100% | 100% |
| Fixed window | 55.0 | 96.94% | 50% | 0% | 0% |
| Structured compaction | 301.9 | 83.20% | 100% | 100% | 100% |

结构化压缩保留状态摘要、近期消息和 Artifact 引用，原始工具事件仍可恢复。测试还发现并修复了一个真实缺陷：摘要阶段曾读取 artifact 化之前的长工具输出，导致大段正文被重新内联，表面“压缩”实际反弹。现在摘要只读取 artifact 化后的视图。

该实验能够证明 Token 与信息保持的机制权衡，不能证明回答质量提升。回答事实正确率和引用支持率要等人工审核答案探针后再报告。

## 对 Claude Code 与 Hermes 思路的借鉴

- 借鉴 Claude Code 的分层上下文思想：当前状态与近期消息留在 prompt，长工具结果外置为可恢复 Artifact。
- 借鉴 Hermes 的会话搜索/压缩思想：压缩结果不是不可追溯纯摘要，必要时可按事件和 Artifact 恢复原文。
- PaperStorm 的补充：把约束、实体、来源、工具配对、重复压缩漂移和 restore 做成确定性指标，并设置失败回退。

这里应表述为“参考设计思想并完成独立实现和对照评测”，不能声称复用了 Claude Code 私有源码，也不能把 Context 指标当成对 Claude/Hermes 的性能胜负比较。

## 面试可讲内容

1. 为什么按论文而不是 chunk 划分：防止同一论文相邻 chunk 同时进入 dev/test，造成检索泄漏。
2. 为什么 Hybrid 不一定全面优于 Dense：词法与语义融合可能提高 Recall，但权重、query 分布和语料噪声会影响 MRR。
3. 为什么 Rerank 没默认上线：离线 nDCG 提升不等于可部署，必须同时满足召回下降容忍和 P95 延迟预算。
4. 为什么不能只报均值：55 条候选仍是小样本，Bootstrap CI 能表达不确定性。
5. 为什么固定窗口不是合格压缩：它节省 Token 最多，却丢失一半约束和全部来源，且无法恢复工具证据。
6. 如何治理 benchmark：人工审核、哈希失效、dev 选型、冻结 test 门禁、证据等级和脱敏聚合报告。

## 当前需要人工完成

在网页开发者控制台打开“v5.4 真实论文 RAG 与 Context Engineering”，逐条审核 test 候选：

1. 判断问题是否自然有效；不自然则选择“需要改写”并填写改写问题。
2. 检查相关论文 ID 是否正确，可添加多个真实相关论文，减少 false negative。
3. 检查证据是否足以回答问题，并记录歧义或缺陷。
4. 至少完成 50 条有效 test 审核后，重新运行真实检索实验。

审核前不要在简历使用冻结 test 分数。当前可写的是：搭建了真实 PDF、文档级隔离、人工审核门禁、Bootstrap CI、条件式 Rerank 和可恢复 Context 的评测系统，并通过 dev 实验识别了质量/延迟权衡。
